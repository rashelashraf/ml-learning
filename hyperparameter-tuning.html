Hyperparameter Tuning

Search the settings you choose, not the parameters the model learns

Home / Hyperparameter Tuning

1 Parameters vs Hyperparameters

A model has two kinds of numbers. It learns one kind from the data during training. You choose the other before training starts — those are the hyperparameters, and tuning them is what this page is about.

Parameters — learned

  • Fitted by the optimiser from training data
  • Weights and biases, split thresholds, support vectors
  • Can number in the millions
  • You never set them by hand
model.coef_, model.intercept_

Hyperparameters — chosen

  • Fixed before the fit; control how learning happens
  • Learning rate, tree depth, regularisation strength, k
  • Usually a handful that actually matter
  • Found by searching, not by gradient descent
max_depth=6, learning_rate=0.05
Why this matters: hyperparameters set the bias–variance dial. Too much capacity (deep trees, tiny regularisation) and the model memorises the training set; too little and it never learns the signal. Tuning is the search for the setting that generalises best — measured on data the model has not seen.

2 What to Tune, by Model Family

You rarely need to tune everything. Start with the two or three hyperparameters that dominate performance for your model, then widen the search only if the gains justify the compute.

📈 Linear & Logistic

  • C / alphaRegularisation strength — the main dial
  • penaltyL1 for sparsity, L2 for shrinkage, elastic-net for both
  • solverAffects speed and which penalties are legal

Search C on a log scale — 0.001 to 100.

🌳 Trees & Forests

  • max_depthThe single biggest overfitting control
  • min_samples_leafFloor on leaf size; smooths predictions
  • max_featuresDe-correlates trees in a forest
  • n_estimatorsMore is rarely worse, just slower

For forests, tune depth and max_features first.

⚡ Gradient Boosting

  • learning_rateLower is better but needs more rounds
  • n_estimatorsTrades off directly against learning rate
  • max_depth3–8 is the usual sweet spot
  • subsampleRow sampling adds useful randomness

Fix a small learning rate, then use early stopping to pick the round count.

🧠 Neural Networks

  • learning_rateDominates everything else — tune it first
  • batch_sizeInteracts with learning rate
  • hidden units / depthCapacity of the network
  • dropout / weight_decayRegularisation

Learning rate on a log scale beats almost any other single change.

How quickly each strategy converges. Run several strategies to compare them on the same axes.

Strategy How it picks the next trial Best for Cost
Grid Every combination on a fixed lattice 1–2 hyperparameters, small discrete sets Explodes exponentially with dimensions
Random Samples independently from each range Sensible default; 3+ hyperparameters Same as your budget, and parallel
Bayesian Fits a surrogate of the score, samples where it expects gains Expensive fits where every trial counts Sequential, so harder to parallelise
Successive halving / Hyperband Starts many configs cheaply, kills the weak ones early Iterative learners with a budget dial (epochs, trees) Very efficient when partial results predict final ones
Watch what happens as you drag the budget slider. Random search improves smoothly — every extra trial is a new value of every hyperparameter. Grid search lurches: it does well when the lattice happens to land near the optimum (try 16, 36 and 64, the perfect squares) and poorly when it straddles it. You cannot know in advance which you will get, because you do not know where the optimum is — that is the whole point of searching.
And this is only two dimensions. Here grid and random are roughly even on average. The classic result (Bergstra & Bengio, 2012) is that random search pulls decisively ahead as you add hyperparameters, because real objectives have low effective dimensionality — only a couple of hyperparameters really matter. A 4×4×4 grid tests just 4 distinct learning rates using 64 trials; random search tests 64. Bayesian optimisation wins at every budget above because it spends its trials where the surrogate predicts gains, but it is sequential and therefore harder to parallelise.

5 Tuning Without Fooling Yourself

Every time you look at a score and change something, you leak a little information from that split into your model. Tune on validation folds; report on a test set you touched exactly once.

Each candidate setting is scored by averaging across the inner folds.

The most common leak: fitting a scaler, encoder or feature selector on the whole dataset before splitting. The transform then carries information from the validation rows, and your tuned score comes out optimistic. Put every preprocessing step inside a Pipeline so it is refitted within each fold. 
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.ensemble import RandomForestClassifier
from sklearn.model_selection import RandomizedSearchCV, cross_val_score

pipe = Pipeline([
    ("scale", StandardScaler()),          # refitted inside every fold
    ("clf",   RandomForestClassifier(random_state=0)),
])

search = RandomizedSearchCV(
    pipe,
    {                                     # note the "step__param" naming
        "clf__max_depth":        [3, 5, 8, 12, None],
        "clf__min_samples_leaf": [1, 2, 4, 8],
        "clf__max_features":     ["sqrt", "log2", 0.5],
    },
    n_iter=40,                            # budget, not the full grid
    cv=5,                                 # inner loop
    scoring="roc_auc",
    random_state=0,
    n_jobs=-1,
)

# outer loop: an honest estimate of the *tuning procedure*
scores = cross_val_score(search, X, y, cv=5, scoring="roc_auc")
print(f"nested CV: {scores.mean():.3f} +/- {scores.std():.3f}")

6 A Practical Playbook

1

Get a baseline first

Fit the model on defaults and record the score. Tuning that cannot beat the default is telling you the problem is elsewhere — usually in the features.

2

Search wide and coarse before narrow and fine

Use log scales for anything spanning orders of magnitude. A coarse pass tells you which region deserves the budget.

3

Tune the few that matter

Learning rate for boosting and networks; depth and leaf size for trees; regularisation for linear models. Adding a fourth or fifth rarely pays.

4

Check the winner is not on a boundary

If the best value sits at the edge of your range, the range was too narrow. Extend it and search again.

5

Prefer the simpler setting when scores tie

Differences inside the fold-to-fold standard deviation are noise. Take the shallower tree, the stronger regularisation, the smaller network.

6

Refit on all the data, then report once

Retrain the chosen setting on train + validation, then evaluate on the held-out test set a single time.

Pitfalls Worth Knowing

Tuning on the test set

  • Every peek at test performance is a tuning decision
  • The score stops being an estimate of future performance
  • Keep a split you evaluate exactly once

Chasing noise

  • With enough trials, some setting wins by luck alone
  • Compare against the fold-to-fold standard deviation
  • Repeat the search with a different seed to check it holds

The wrong metric

  • Accuracy on imbalanced data rewards predicting the majority
  • Tune the metric you actually care about
  • Use the same metric for search and for reporting

Ignoring the budget

  • Doubling trials for +0.001 AUC is rarely worth it
  • Better features usually beat better hyperparameters
  • Set a stopping rule before you start
